1核心概念：为什么用 Docker

嵌入式 Linux 开发需要一个 Linux 构建环境（编译 Buildroot、跑交叉工具链）。Mac 是 macOS 系统，不能原生完成全部工作。有两种方案：

虚拟机（Parallels/UTM）Docker 容器（本指南采用）
本质虚拟一整套电脑，含完整 Ubuntu 内核一个"工具箱"，借用 macOS 内核
资源占用内存 2-4 GB，磁盘 20 GB+内存几百 MB，磁盘约 1 GB
启动速度30-60 秒约 1 秒
文件共享需配置共享文件夹目录直接挂载，双向同步

生活化类比：你要喝一杯咖啡（编译工具），虚拟机是为此租了一整套公寓；Docker 是把咖啡机直接放在自家厨房台面——咖啡机一样，搭建的成本天差地别。

本指南最终构建的 SAMA5D27 启动链：

Boot ROM（芯片固化）→ AT91Bootstrap→ U-Boot→ Linux 内核→ 根文件系统

其中中间三环都在容器里交叉编译产出，最后在 Mac 上 dd 烧录到 SD 卡。

2安装 Docker Desktop（Mac）

Docker Desktop 是 Docker 的官方 Mac 桌面应用。由于 macOS 安全限制，建议手动下载安装（brew 安装可能被权限机制拦截）。

步骤 2.1：下载安装包

浏览器打开官网 https://www.docker.com/products/docker-desktop/，选择 Download for Mac (Apple Silicon)（M 系列芯片）。

步骤 2.2：安装

  1. 双击下载的 Docker.dmg
  2. 把 Docker 图标拖入 Applications 文件夹
  3. 从启动台打开 Docker.app，首次启动点"允许"权限请求
  4. 接受服务条款，可跳过登录（Skip / Continue without signing in）
  5. 等菜单栏出现 🐳 鲸鱼图标，显示 "Docker Desktop is running"

步骤 2.3：验证安装

在 Mac 终端执行
docker --version
  • docker --version — 查看 Docker 版本号。输出类似 Docker version 27.x.x 即安装成功。
检查 Docker 后台服务是否在运行
docker info --format '{{.ServerVersion}}'
  • docker info — 查询 Docker 后台守护进程的状态。--format 只提取版本号字段。
  • 如果这条命令报错，说明 Docker Desktop 应用没有启动——去菜单栏点开鲸鱼图标启动它。

3安装串口工具与创建工作目录

步骤 3.1：安装 Homebrew（如果没有）

在 Mac 终端执行
# 先检查是否已有 brew
which brew
  • which brew — 查找 brew 命令的位置。有输出说明已安装；无输出则去 brew.sh 按官方指引安装。

步骤 3.2：安装 picocom（串口终端）

在 Mac 终端执行
brew install picocom
  • brew install 包名 — 用 Homebrew 安装软件。
  • picocom 用于连接开发板调试串口。它装在 Mac 本地（不装在容器里），因为串口设备插在 Mac 上。
  • 后续连接开发板：picocom -b 115200 /dev/ttyACM0（115200 是波特率）。退出按 Ctrl+A 再按 Ctrl+X。

步骤 3.3：创建工作目录

在 Mac 终端执行
mkdir -p ~/sama5
  • mkdir — 创建目录（make directory）。
  • -p — 递归创建，且目录已存在时不报错。
  • ~/sama5 — ~ 是家目录的缩写（即 /Users/你的用户名）。这个目录将作为 Mac 与容器的共享桥梁。

4编写 Dockerfile 并构建镜像

Dockerfile 是"镜像的配方"——描述这个 Ubuntu 环境里要装哪些工具。用任意编辑器创建文件 ~/sama5/Dockerfile，内容如下：

FROM ubuntu:22.04

ENV DEBIAN_FRONTEND=noninteractive

RUN apt update && apt install -y \
    build-essential git wget curl flex bison bc \
    libssl-dev libncurses-dev device-tree-compiler \
    u-boot-tools gcc-arm-linux-gnueabihf \
    python3 python3-pip rsync chrpath cpio \
    libgnutls28-dev picocom minicom gdb-multiarch

逐行说明：

  • FROM ubuntu:22.04 — 以官方 Ubuntu 22.04 镜像为基础（LTS 长期支持版，Buildroot 官方推荐的构建环境）。
  • ENV DEBIAN_FRONTEND=noninteractive — 安装软件时不弹交互式问答窗口（容器里没有图形界面）。
  • RUN apt update && apt install -y ... — 更新软件源后安装所有编译工具。-y 表示自动回答 yes。

关键软件包用途：

  • gcc-arm-linux-gnueabihf — 交叉编译器，最重要的一个。在你的 Mac 上生成 ARM 32 位指令集的可执行文件。
  • build-essential — make、gcc 等基础编译工具。
  • device-tree-compiler — dtc，编译设备树（.dts → .dtb）。
  • u-boot-tools — 提供 mkimage，打包 U-Boot 镜像。
  • flex bison bc libssl-dev libncurses-dev — 内核编译依赖（语法生成器、计算器、加密库、menuconfig 界面库）。
  • libgnutls28-dev — U-Boot 新版编译必需（缺少会报 gnutls/gnutls.h: No such file 错误，实战踩过的坑）。

步骤 4.1：构建镜像

在 Mac 终端执行（注意先进入 ~/sama5 目录）
cd ~/sama5
docker build -t sama5-build .
  • cd ~/sama5 — 进入工作目录。docker build 会在当前目录找 Dockerfile。
  • docker build — 按 Dockerfile 构建镜像。
  • -t sama5-build — 给镜像起名字（tag），方便以后引用。
  • . — 构建上下文是当前目录。
  • 首次构建需下载 Ubuntu 镜像并安装软件，约几分钟。

5启动容器与快捷入口

步骤 5.1：创建并启动容器

在 Mac 终端执行
docker run -d --name sama5-dev \
  -v "$HOME/sama5:/work" \
  -w /work \
  sama5-build \
  sleep infinity

参数逐个解释：

  • docker run — 用镜像创建并启动一个容器。
  • -d — 后台运行（detached），不占用当前终端。
  • --name sama5-dev — 容器命名为 sama5-dev，以后用名字引用它。
  • -v "$HOME/sama5:/work" — 目录挂载，最关键的参数。把 Mac 的 ~/sama5 目录映射为容器内的 /work。两边看到的是同一个文件夹：容器里编译出的文件，Mac 上立刻可见。
  • -w /work — 进入容器后默认所在的工作目录（working dir）。
  • sama5-build — 使用哪个镜像。
  • sleep infinity — 容器启动后执行的命令。让容器永远保持运行（否则命令结束容器就停了）。

步骤 5.2：创建快捷入口脚本

每次输入上面一长串太麻烦。创建 ~/sama5/enter.sh：

#!/bin/bash
# 如果容器没在运行，先启动它
docker start sama5-dev 2>/dev/null
# 进入容器的交互式终端
docker exec -it sama5-dev bash
  • #!/bin/bash — 脚本固定首行，声明用 bash 解释执行。
  • docker start sama5-dev 2>/dev/null — 启动容器（若已在运行则无操作），错误输出丢弃。
  • docker exec -it sama5-dev bash — 在已运行的容器里开一个交互式（-it）bash 终端。
赋予脚本可执行权限
chmod +x ~/sama5/enter.sh
  • chmod +x — 给文件添加可执行权限（否则提示 Permission denied）。

步骤 5.3：进入容器

以后每次进入容器，只需一条命令
~/sama5/enter.sh
  • 执行后提示符从 用户名@Mac ~ % 变成 root@容器ID:/work#，说明你已在容器内的 Ubuntu 环境中。
  • 可以同时开多个终端执行 enter.sh——多个"门"通向同一个容器，互不干扰。适合一边跑编译一边干别的。

6进入容器：环境变量配置

编译前必须设置两个环境变量，告诉编译系统"用什么交叉编译器、目标什么架构"。

在容器内执行
export CROSS_COMPILE=arm-linux-gnueabihf-
export ARCH=arm
  • export 变量=值 — 设置环境变量，当前终端及其子进程可见。
  • CROSS_COMPILE=arm-linux-gnueabihf- — 交叉编译器的"前缀"。编译系统调用编译器时会自动拼成 arm-linux-gnueabihf-gcc、arm-linux-gnueabihf-ld 等。注意结尾的 - 不能少。
  • ARCH=arm — 目标架构是 ARM 32 位（SAMA5D27 是 Cortex-A5 核心）。
  • 不设置会报错：Error: the CROSS_COMPILE environment variable must be defined（实战踩坑）。
💡 一劳永逸写法

export 只对当前终端有效，重开终端要重新设。写进 bashrc 自动生效：

echo 'export CROSS_COMPILE=arm-linux-gnueabihf-' >> ~/.bashrc
echo 'export ARCH=arm' >> ~/.bashrc

>> 表示追加到文件末尾（~/.bashrc 是容器内 bash 每次启动自动读取的配置文件）。注意：这里的 ~ 指容器内的 /root，别和 Mac 的家目录混淆。

验证交叉编译器

在容器内执行
arm-linux-gnueabihf-gcc --version
echo "int main(){return 0;}" > /tmp/t.c && arm-linux-gnueabihf-gcc -o /tmp/t /tmp/t.c && file /tmp/t
  • 第一条显示编译器版本。
  • 第二条做一个最小测试：写一个 hello world → 交叉编译 → file 查看产物格式。输出包含 ELF 32-bit LSB ... ARM 说明工具链工作正常。

7编译 AT91Bootstrap（第一级引导）

AT91Bootstrap 是芯片上电后 Boot ROM 最先加载的程序，负责初始化 DDR 内存、加载 U-Boot。

步骤 7.1：克隆源码

在容器内执行
cd /work
git clone https://github.com/linux4sam/at91bootstrap.git
cd at91bootstrap
  • cd /work — 回到共享目录根，源码都放这里。
  • git clone URL — 从 GitHub 下载完整源码仓库到当前目录下的 at91bootstrap/ 文件夹。URL 必须完整，结尾是 .git——曾因少打一个 t（.gi）导致 git 把它当成不存在的仓库、要求输入用户名密码（实战踩坑）。

步骤 7.2：加载板级配置

在容器内执行
make mrproper
make sama5d27_som1_eksd_uboot_defconfig
  • make mrproper — 清理所有编译产物和旧配置，回到干净状态。首次编译可省略，但重复编译前建议执行。
  • make xxx_defconfig — 加载一份"默认配置"。配置名可拆解：sama5d27_som1_ek = 开发板型号；sd = 从 SD 卡启动；uboot = 下一步引导 U-Boot。
  • 想看所有可用配置：ls configs/ | grep sama5d27

步骤 7.3：编译

在容器内执行
make -j$(nproc)
  • -j$(nproc) — 并行编译。$(nproc) 会被替换成 CPU 核心数，几个核心就同时跑几个编译任务，大幅加速。
  • 编译约 1-2 分钟。成功的标志是输出：
[Succeeded] It's OK to fit into SRAM area

这条表示镜像大小能装进芯片的 SRAM（硬性约束）。同时会显示给栈留了多少空间。

步骤 7.4：确认产物

在容器内执行
find . -name "*.bin" -ls
  • find . -name "*.bin" — 在当前目录递归查找所有 .bin 文件。-ls 用长格式显示详情。
  • 产物在 build/binaries/ 下（注意：4.0.x 新版路径和老版不同，老版直接在 binaries/）。主要文件：sama5d2-sdcardboot-uboot-4.0.x.bin（约 17KB），旁边的 at91bootstrap.bin、boot.bin 都是它的软链接。

8编译 U-Boot（第二级引导）

U-Boot 是通用 Bootloader，负责加载 Linux 内核，并提供一个串口命令行（开发阶段最重要的调试入口）。

步骤 8.1：克隆并配置

在容器内执行
cd /work
git clone https://github.com/linux4sam/u-boot-at91.git
cd u-boot-at91
make sama5d27_som1_ek_mmc_defconfig
  • sama5d27_som1_ek_mmc_defconfig — 板型 + mmc（SD 卡）介质的默认配置。

步骤 8.2：编译

在容器内执行
make -j$(nproc)
  • 约 5-10 分钟。若报错 fatal error: gnutls/gnutls.h: No such file or directory，装库后重编：
apt update && apt install -y libgnutls28-dev
make -j$(nproc)

（Dockerfile 里已包含此包，此坑一般不会再现；重编不需要 make clean。）

步骤 8.3：验证产物

在容器内执行
ls -lh u-boot.bin
file u-boot.bin
  • ls -lh — -l 长格式，-h 人类可读的大小（K/M/G）。正常 u-boot.bin 约 470KB。
  • 注意：此配置下没有 spl/u-boot-spl.bin 是正常的——SAMA5D27 用 AT91Bootstrap 做第一级引导，不需要 U-Boot 的 SPL。

9编译 Linux 内核与设备树

步骤 9.1：克隆内核源码（大工程，耐心）

在容器内执行
cd /work
git clone https://github.com/linux4sam/linux-at91.git
  • 内核仓库约 3.6 GB、1200 万个对象，克隆十几分钟。下载分两个阶段：
  • Receiving objects — 从服务器传输压缩数据（下载）。
  • Resolving deltas — 本地解析差分对象（组装）。git 为省空间不存每个文件的每个完整版本，只存"基础版本 + 差异记录"，此阶段就是把差异链还原、建立引用关系。
⚠️ 千万不要中途 Ctrl+C

必须等 Resolving deltas: 100% 出现且提示符回来。打断会让仓库残缺，只能删除重来：

rm -rf linux-at91

之后重新 clone。rm -rf 是递归强制删除，路径一定要确认无误再回车。

步骤 9.2：切换分支

在容器内执行
cd linux-at91
git checkout linux-6.1-mchp
git branch
  • 仓库里同时保存多条开发线（分支）：克隆后默认在 master。linux-6.1-mchp 是 Microchip 维护的 6.1 稳定分支，官方推荐用于 SAMA5D2。
  • git checkout 分支名 — 把工作目录的文件内容替换成该分支的版本。
  • git branch — 查看当前所在分支，带 * 的是当前分支。

步骤 9.3：加载配置并编译

在容器内执行
make sama5_defconfig
make -j$(nproc)
  • make sama5_defconfig — 加载 SAMA5 全系列默认内核配置（含各开发板支持）。
  • make -j$(nproc) — 编译。约 10-20 分钟，期间大量刷屏是正常现象。
  • 编译时可以切走：新开终端标签（Mac 终端按 Cmd+T）干别的，互不影响；但不要关闭原窗口、不要按 Ctrl+C/Z。
  • 更保险的后台跑法：nohup make -j$(nproc) > build.log 2>&1 &，用 tail -f build.log 看进度。
  • 若需自定义配置（添加驱动、协议等），在编译前执行 make menuconfig 打开图形化配置界面。

11Buildroot 构建与烧录上板

内核 + 引导都编译好之后，还差最后一环：根文件系统（rootfs）——内核启动后要挂载的"系统盘"，没有它内核会直接 panic。Buildroot 会自动把引导、内核、设备树、rootfs 打包成一个布局正确的完整 SD 卡镜像，一条 dd 就能烧录，无需手工摆放文件。

💡 我手动编译的三件套白做了吗？

没有白做，但要明白一件事：Buildroot 是一站式全量构建——它会按自己的配置重新编译一份 AT91Bootstrap、U-Boot、内核和设备树，最终 sdcard.img 里装的是 Buildroot 编的那套，而不是你手动编译的产物。

手动编译的价值在于学习和理解：走完第 7-9 节，你就清楚启动链每一环是什么、怎么编译出来的、产物长什么样。今后想单独替换内核或 U-Boot 做调试时（改一行内核代码重新 make 再单独烧 zImage），这些手动技能就是日常工作的基本盘。

第一次上板验证，直接用 Buildroot 的完整镜像即可，最省心。

深入理解：rootfs 为什么不像内核那样"单独 make"就行？

常见误解是"根文件系统必须用 Buildroot"。实际上 rootfs 完全可以单独构建，Buildroot 只是自动化工具。但它和前三样（引导/内核）有本质区别，导致单独构建的难度完全不在一个量级——一个是在"编译"，一个是在"组装"：

对比项引导 / 内核根文件系统
形态 一个源码仓库，一个编译产物 几百个软件包的集合，拼成一棵目录树
源码 at91bootstrap / u-boot / linux 各自一个 git 仓库 busybox、libc、openssl……每样来自不同项目
构建方式 make defconfig + make 一条龙 每个包有自己的构建系统，交叉编译各有各的坑
产物 一个 .bin / zImage 一棵目录树（/bin /lib /etc /dev...），再打成镜像

AT91Bootstrap 和内核再复杂，也是"一个项目编译出一个文件"。而 rootfs 是"把几百个用户态程序 + 库全部交叉编译好、装进正确目录"——这活不是编译，是包管理。手工做为什么会痛苦：

  • 架构不匹配 — 每个包都要用 arm-linux-gnueabihf-gcc 重新编译，各项目对交叉编译的支持参差不齐；
  • 依赖地狱 — openssl 依赖 zlib、每个 app 依赖 libc……必须按正确顺序逐个编译安装；
  • sysroot 路径问题 — 编译时找头文件、链接时找库，路径一错就是各种诡异的 file not found；
  • 运行时文件 — /dev 设备节点、/etc/inittab、启动脚本、权限……全要手工摆。

Buildroot 的价值就是把这套"逐包交叉编译 + 依赖排序 + 装目录 + 生成镜像"的脏活全自动化（Yocto 干的是同一件事，更工业级也更复杂）。

进阶：不用 Buildroot，手工做一个最小 rootfs（推荐试一次）

最小系统能小到什么程度？一个 busybox 就够了——它一个程序内嵌了 ls/cd/cp/sh 等三百多个常用命令。走一遍这个流程，你会彻底搞懂 rootfs 就是一棵目录树，没有任何魔法。

make CROSS_COMPILE=arm-linux-gnueabihf- CONFIG_PREFIX=/work/my-rootfs install
  • make defconfig — 启用几乎全部功能的默认配置。
  • CONFIG_PREFIX=/work/my-rootfs — 把 busybox 及其命令链接安装到该目录（生成 bin/ sbin/ usr/ 等结构）。
容器内 · 手工补齐目录、设备节点与启动配置
cd /work/my-rootfs
mkdir -p dev etc proc sys tmp
mknod -m 666 dev/console c 5 1
mknod -m 666 dev/null c 1 3
  • dev/console — 内核的控制台设备，没有它 init 起来也没有输出。
  • dev/null — 大量程序默认会写它，缺失会报错。

echo "::sysinit:/bin/mount -t proc proc /proc" > etc/inittab

  • 把这个 64MB 镜像写入 SD 卡第二分区，配合前面的内核即可启动到一个纯 busybox 的 shell。

  • nohup make ... & — 这条才是真正开始编译的命令。下面逐个拆开讲：
📖 命令拆解：7 个零件，一个一个看（点开展开）

完整命令

完整命令：nohup make O=/root/br-out -j$(nproc) > /root/build.log 2>&1 &

零件是什么在这里为什么需要它
nohup No Hang UP 的缩写，"别挂断" 如果你不小心关了终端窗口、或者 SSH 断了，进程默认会被杀掉。nohup 给进程套了件"防弹衣"，终端关了它也不死，继续在后台编译。
make 构建工具，读 Makefile 里写的规则来编译 Buildroot 就是用 Makefile 组织的，make 是启动编译的总开关。
O=/root/br-out Output 目录参数 告诉 Buildroot：所有编译产物写到 /root/br-out（容器自己的地盘），而不是当前目录的 output/。这是绕开 Permission denied 的关键——详见上方"深入理解"。
-j$(nproc) -j = 并行编译，$(nproc) = 自动获取 CPU 核数 不给 -j 就是单核串行编译，慢得要命（可能 4-5 小时）。$(nproc) 会自动数你的容器有多少个 CPU 核，比如 8 核就等价于 -j8，同时跑 8 个编译任务，时间缩短到 1-2 小时。
> /root/build.log 标准输出重定向，> = "写到文件" 把编译时吐出来的文字改道写进文件，而不是喷到屏幕上。详细原理见下方「大白话讲重定向」。
2>&1 标准错误也并进来，2 = 错误流，&1 = 跟标准输出走同一条路 Linux 有两个输出通道：①正常信息（stdout，编号 1）②报错信息（stderr，编号 2）。> 只接 ①，错误信息还是会喷到屏幕。2>&1 的意思是"把 ② 也塞进 ① 那条管子里"，这样正常和错误信息全都进日志文件，一个都不漏。
&（行末最后那个） 后台运行符 没有这个 &，终端会卡住等编译完才能输入下一条命令。加了 &，编译立刻丢到后台跑，终端马上还给你，你可以接着输入 tail -f 看进度。
整条命令翻译成人话：

"用 nohup 保护着，启动 make 编译，产物放到 /root/br-out，用全部 CPU 核并行跑（-j$(nproc)），正常输出和错误信息都写进 /root/build.log（> ... 2>&1），然后把这事扔到后台（&），我终端还要干别的。"

敲完之后会看到什么？

终端立刻回一行类似 [1] 12345。[1] 是后台任务编号，12345 是进程号（PID）。看到这行就说明编译已经成功在后台启动了——然后紧接着跑 tail -f /root/build.log 去看实时进度即可。

大白话讲重定向：为什么需要 >？

先搞懂一件事：程序的"输出"默认去哪？

你在终端里敲一个命令，比如 echo hello，屏幕上就打印出 hello。这不是魔法——每个程序天生有一根"管子"，一头连着自己，另一头默认连着屏幕。程序吐出的所有文字，顺着这根管子流到屏幕上，你就看到了。

程序 (make) ──吐字──▶ 屏幕（终端窗口）

↑ 这就是"默认行为"：管子的出口接在屏幕上，字全部喷到你眼前。

问题是：编译会吐几万行字

Buildroot 编译不是吐一两行，是几万行。每一行就是"我在编译这个文件""我在链接那个库""我在下载这个包"……全部顺着管子流到屏幕上，你终端就像下面这样疯狂滚动：

$ make -j$(nproc)
  CC      fs/exec.o
  CC      fs/pipe.o
  CC      fs/namei.o
  CC      fs/fcntl.o
  CC      fs/mbcache.o
  LD      fs/built-in.o
  CC      kernel/sched/core.o
  CC      kernel/sched/fair.o
  CC      kernel/sched/rt.o
  ...（还有几万行，刷到你根本看不清，也找不到重点）
  ...（而且终端被占住了，你没法输入别的命令）
$

↑ 不加 > 时，屏幕长这样：字疯狂滚动，终端卡死等编译完。

> 做了什么？——把管子的出口从"屏幕"拧到"文件"

> 这个符号，就是一个"管道扳手"。它把程序那根管子的出口，从"屏幕"拧下来，接到一个文件上。程序还是照常吐几万行字，但这些字全部流进了文件，屏幕上一滴都不漏出来。

程序 (make) ──吐字──▶ build.log 文件 📄

↑ 加了 > 后：管子出口接到了文件，屏幕上什么都不会显示。

加 > 后，屏幕长这样：

$ nohup make ... > /root/build.log 2>&1 &
[1] 12345
$    ← 就这一行，干干净净。几万行字全进了 build.log，屏幕上看不到。
     你可以接着输入别的命令，终端没有被占住。

↑ 加了 > 时，屏幕长这样：干净，终端马上还给你。

那我想看编译进度怎么办？

字都进了文件，但你可以用 tail -f /root/build.log 去"翻看"这个文件——它会实时显示文件里新写进来的行，效果和直接喷到屏幕一样，但你可以随时 Ctrl+C 退出查看，不影响编译。不想看了就退出，想看了再 tail -f 一次，编译一直在后台跑，不受影响。

再补充：重定向符号 > 和 2>&1 的技术原理

Linux 每个程序默认有三条管子连着终端：

编号名字默认去哪
0stdin（标准输入）键盘打字 → 程序
1stdout（标准输出）程序 → 屏幕（正常信息）
2stderr（标准错误）程序 → 屏幕（报错信息）

命令里的重定向做了两步：

  • > /root/build.log — 把管子 1（正常输出）的出口从"屏幕"改到"文件"。
  • 2>&1 — 把管子 2（错误输出）的出口接到管子 1现在去的地方（也就是文件）。
你可能想问：为什么 > 前面没有写 1？

因为 > 就是 1> 的简写。规则很简单：

  • 1> 文件 — 重定向 1 号管子（正常输出），写完整版
  • > 文件 — 同上，省略了 1，因为 1 是默认值，不写就代表 1
  • 2> 文件 — 重定向 2 号管子（错误输出），必须写 2，因为 2 不是默认值

所以 > /root/build.log 和 1> /root/build.log 完全等价，只是大家嫌麻烦，把 1 省了。但 2>&1 里的 2 不能省——省了就变成 >&1，意思就完全变了。

结果：正常信息和错误信息全部流进同一个文件，屏幕上干干净净，但你想查什么都不会丢。

  • tail -f /root/build.log — 只是"看日志"，不负责启动编译。实时显示编译进度，按 Ctrl+C 只退出查看、不会中断后台编译。想再回去看就再跑一次这条。
📖 深入理解：为什么 /work 会报 Permission denied，为什么要搬到 /root？

1. 先理清"谁的地盘"

你 Mac 硬盘上有个文件夹 ~/sama5。Docker 启动容器时，把 Mac 上 ~/sama5 映射成容器里的 /work。两边看到的是同一份文件——容器里改，Mac 上也变；Mac 上改，容器里也变。

/work = ~/sama5（同一份文件的两个入口）

2. 为什么有"死规矩"

这些文件终究还是 Mac 的文件，文件身上的属性（比如"能不能执行"这种标记）是 Mac 的文件系统说了算，容器说了不算。Docker 出于安全考虑，定了一条规则：容器不能去改 Mac 文件身上的权限属性。

类比

你把家里的书借给朋友看。朋友可以翻、可以在空白处写字，但你规定：不许给书包书皮、不许改封皮颜色。书是你的，外观属性你说了算，朋友只能动内容。"可执行"这个标记，就相当于"书的封皮颜色"。朋友（容器）想把它改成绿色（可执行），你（Mac 文件系统）不让。

3. 编译为什么会卡在这条规矩上

Buildroot 编译时会当场写一个脚本出来，写完马上就要运行它（如 e2fsprogs 的 compile_et）。这个脚本写在 output/ 里，而 output/ 在 /work 下面 → 也就是 Mac 的文件上：

Buildroot: "我写好脚本了，现在执行它"
文件系统:  "这个文件没有可执行标记"
Buildroot: "那我给它加上"
文件系统:  "这是 Mac 的文件，你不许改标记"
Buildroot: "……"  → Permission denied (Error 126)

chmod +x 也改不了——因为 chmod 本身就是在"改 Mac 文件的权限属性"，同样被拒绝。

4. 为什么搬到 /root 就解决了

/root 是容器自己的地盘，不在 Mac 硬盘上，是容器自己虚拟出来的文件系统。在这块地盘上容器是老大：文件想怎么标记就怎么标记，生成的脚本可以立刻打上"可执行"标记，没人拦着。

/work  = Mac 的地盘，借来的，规矩多，不能改文件属性  ✗ 编译会卡
/root  = 容器自己的地盘，自己做主，想怎么改怎么改    ✓ 编译顺畅

所以用 O=/root/br-out 把编译产物放到容器内部，问题就彻底消失了。源码（只读不执行，不受影响）留在 /work，各放各的地方互不打架。

各命令的分工一览
命令做了什么编译开始了吗
make ...defconfig加载配置（几秒完成）否，只是配置
nohup make ... &这条才真正开始编译，输出写到日志文件✓ 是
tail -f /root/build.log打开日志实时显示进度不影响编译

执行 nohup ... & 后终端会回一行 [1] 12345（数字是进程号），就说明后台编译已启动。此时跑 tail -f 就能看到不断滚动的日志。编完会出现 Done 字样并停下来。

📖 深入理解：sdcard.img 里的 MBR（主引导记录）是什么？（点击展开）

编译日志最后一步会显示 writing MBR。MBR（Master Boot Record，主引导记录）是 SD 卡的第一个扇区，也就是整张卡最开头的 512 个字节。

用一本书来比喻：SD 卡就像一本厚书，MBR 就是这本书的目录页。目录页告诉你这本书分了几个章节（分区）、每个章节从第几页开始（分区起始位置）、每个章节有多长（分区大小）。板子上电后，Boot ROM 做的第一件事就是翻到"目录页"（MBR），看看这张卡是怎么分的、启动分区在哪，然后才知道去哪里找 boot.bin。

MBR 里装了什么？（总共 512 字节，分三部分）

部分 大小 作用
启动代码 446 字节 一小段程序，告诉硬件"去哪个分区找引导程序"
分区表 64 字节 记录这张卡分了几个区、每个区从哪开始、多大
魔数 2 字节 固定值 0x55AA，相当于盖个章，表示"这是一张有效的引导卡"

你的 sdcard.img 为什么需要写 MBR？

Buildroot 生成 sdcard.img 时，把两个分区装进了同一个镜像文件：

sdcard.img（137MB）
├── MBR（512 字节）          ← 目录页：告诉你下面有两个分区
├── 分区 1：boot.vfat（16M）   ← 启动分区：zImage + dtb + boot.bin + u-boot.bin
└── 分区 2：rootfs.ext4（120M）← 根文件系统分区：Linux 运行需要的所有文件

writing MBR 就是把那张"目录页"写到镜像最开头。如果不写 MBR，板子的 Boot ROM 插上 SD 卡后翻第一页发现是空的，不知道分区在哪，就直接报错启动不了。

一句话总结：MBR 就是 SD 卡开头的 512 字节"目录页"，告诉板子这张卡怎么分的、启动分区在哪。Buildroot 最后一步 writing MBR 就是把这个目录页写好，让 SD 卡能被板子识别和启动。

排坑：板子通电但 Mac 认不到 USB 设备

现象：J10 口插上 USB 线后，板上 D4 LED 闪烁（说明 J-Link-OB 芯片已通电工作），但 Mac 上 ls /dev/tty.usb* 找不到任何设备，ioreg -p IOUSB -l 里也没有 J-Link。

原因 99% 是 USB 线只能充电不能传数据。Micro-B 线外观一模一样，但有些线内部没有数据线芯。判断方法：

  • 以前用这根线连旧手机能在电脑上看到文件 → 能传数据
  • 线比较粗、有屏蔽层 → 通常能传数据
  • 线很细很软、几块钱一根 → 大概率只能充电

换一根确认能传数据的 Micro-B USB 线后，ioreg -p IOUSB -l | grep "USB Product Name" 应能看到 J-Link 字样。

确认板子上的 USB 口

SAMA5D27-SOM1-EK1 板子上有三个 USB 口，只有 J10 是你要找的：

  • J10（Micro-B）→ J-Link-OB 调试 + 串口 + 供电 — 就是这个
  • J17（Micro-AB）→ 板子作为 USB Device — 不用
  • J19（Type-C）→ 板子作为 USB Device — 不用

J10 的 Micro-B 口是最小的那个 USB 口，旁边丝印标着 "J-Link" 或 "DEBUG USB"。用 Micro-B 数据线（老式 Android 充电线那种口）连接 Mac 和 J10，这根线同时供电 + 提供串口，不需要额外电源。

💡 静态链接更稳

默认编出的是动态链接二进制，运行时依赖板子上的 glibc。若板子根文件系统的 glibc 版本比编译器旧，上板会报 version 'GLIBC_2.xx' not found。加 -static 把所有库打进二进制，就能无视版本差异（代价是文件大一些）：

arm-linux-gnueabihf-gcc -static -o hello hello.c

深入理解 7.2a：动态链接 vs 静态链接 —— 二进制到底怎么"依赖"glibc

前面那句"默认编出的是动态链接二进制，依赖板子上的 glibc"可能还是有点抽象，换个说法：

  • 动态链接：编译时只把"我要用 printf / getpid"这件事记进文件，并不把代码本身拷进去。等程序在板子上运行的那一刻，才由系统的动态链接器去借（加载）板子里的 glibc 来用。好处是 100 个程序共用同一份 glibc，省空间；代价是"换根文件系统版本"时可能借不到。
  • 静态链接（加 -static）：编译时就把 printf、getpid 乃至整个 glibc 的机器码复制进你自己的文件。运行时不借任何外部库，自包含，所以换环境也不怕版本问题；代价是文件大（实测 hello 从约 8–15KB 变成 460KB 左右）。
在容器内执行：看清"依赖"到底写在哪里
arm-linux-gnueabihf-readelf -d hello | grep -E 'NEEDED|INTERP'
  • NEEDED libc.so.6 — 运行时必须存在的库清单。动态版写着它；静态版这一行直接消失（库已打进体内）。
  • INTERP /lib/ld-linux-armhf.so.3 — 动态链接器（loader）的路径，由内核在启动程序时负责把它请进来干活。

这就是为什么动态版上板会报 version 'GLIBC_2.xx' not found：板子根文件系统里的 glibc 与编译器自带的版本不匹配，loader 找不到程序要的那个"版本号的 printf"。静态版没有 NEEDED 行，自然不挑版本。

深入理解 7.2b：应用二进制如何"精确"调用到 glibc 里的函数（符号表 + GOT/PLT）

你问得对：ld-linux-armhf.so.3 和 libc.so.6 也都是二进制文件，那你的 hello 怎么知道该跳到它们的哪一行去执行 printf？靠的是名字对接，机制分三步：

在容器内执行：看程序的"待办名单"（动态符号表）
arm-linux-gnueabihf-readelf -sW hello | grep -i printf
  • 符号（symbol） = 函数/变量在库里的名字。你的 hello 在 .dynsym（动态符号表）里登记了一条 printf，状态是"未决/待解析"——只知道名字，不知道地址。
  • 调用 printf 时，代码并不直接跳进 glibc，而是先跳到自己文件里的一段"中转站"：PLT（过程链接表）；PLT 再去查 GOT（全局偏移表） 里存的目标地址。
  • 延迟绑定（lazy binding）：第一次调用 printf 时 GOT 里还是"请 loader 来填"的占位值，于是动态链接器 ld-linux 出场，按名字在 glibc 的 .dynsym 里找到 printf 的真实地址，写进 GOT；此后同一进程再调用 printf 就直达，不再问 loader。
📞 一句话类比

PLT 像你拨号的动作，GOT 像通讯录里存的电话号码；第一次拨 printf 发现通讯录是空的，就由 ld-linux（查号台）按名字查到 glibc 的电话号码填进通讯录，以后再拨就直接通。动态链接器 ld-linux 本身是 ARM 程序，所以 x86 的 qemu 容器里没有它（Could not open /lib/ld-linux-armhf.so.3），动态版才跑不起来——这也解释了为什么 7.3 必须编静态版。

你要做的用的函数头文件坑
开文件fopen(path, "w")<stdio.h>返回 NULL 要判错，perror("fopen") 打印原因
写数字fprintf(f, "255\n")<stdio.h>必须紧跟 fflush(f)！stdio 有缓冲，不 flush 写不进 sysfs

进阶：控制 GPIO 的四种"深度"

你刚写的程序在「应用层」，往下探有四种接口。这正好是第 13 章那 6 层链路的延伸——设备树里 gpios = <&pioA 27 ...> 让内核把 pioA27 配成 LED；你写文件，最终都是驱动去翻转那个 GPIO 的物理寄存器。

层级接口你怎么用坑
① LED 子系统/sys/class/leds/<名>/brightness写 0/1 点灯只能控"被设备树声明为 LED"的引脚（板载红/蓝）；led_blink.c 走这层
② 裸 GPIO sysfs/sys/class/gpio/export + gpioN/{direction,value}export 空闲脚当输入输出板载 LED 脚已被 gpio-leds 独占，这层看不到；Linux 5.18+ 标记 deprecated 但仍能用
③ libgpiod/dev/gpiochipN + gpiod.hgpiod_chip_open/line_request_output/set_value现代 chardev 方式，需板子 rootfs 装 libgpiod（Buildroot 选上）
④ mmap 寄存器/dev/mem 直写 PIO 控制器写 SODR/CODR/OER 寄存器（PIOA 基址 0xFC038000）最硬核、绕开所有驱动、能控任何脚，但写错会搞坏其他功能
想玩外部接的 LED（真·裸 GPIO）？ 把 LED+限流电阻接到板子引出的某个空闲 GPIO 与 GND 之间，用 ② 层：echo N > /sys/class/gpio/export 然后写 direction/value。GPIO 编号 = bank*32 + pin（pioA=bank0，pioB=bank1…）。示例代码思路同上，只是文件路径换成 /sys/class/gpio/gpioN/value。

排坑 2（SSH 密码）：ssh root@IP 弹出 password: 时，要的是在板子串口终端 passwd root 设过的密码，不是字符串 "root"。若提示不对/不记得，回到板子串口终端执行 passwd root 重设（如设 123456），再重新 ssh。能弹出密码框本身说明网络直连和 SSH 服务都已正常，只剩密码这关。

排坑 3（还是 Permission denied）：若重设后仍拒绝，按顺序查：① 确认 passwd root 是在板子串口终端（# 提示符）执行的，而非 Mac/Docker；② 设密码时关掉中文输入法、用纯数字（如 123456），避免全角/特殊字符导致不一致；③ 验证是否真设上：grep '^root:' /etc/shadow，第二字段若是 * 或 ! 说明账户被锁、没设上，若是长哈希串则设好了；④ 极端情况 OpenSSH 禁了 root 密码登录：检查 /etc/ssh/sshd_config 里的 PermitRootLogin 与 PasswordAuthentication 是否为 yes（OpenSSH 默认 prohibit-password），不是则用 sed 改成 yes 并重启 sshd。

排坑 4（Mac 中文输入法吞密码——最常见的隐藏元凶）：Mac 终端在中文（拼音）输入法下敲字母/数字，输入法会吞掉或转换字符，导致实际传给 ssh 的密码和你以为的完全不同，且 ssh 输密码时不显示任何字符（连星号都没有），所以你根本察觉不到。务必在板子设密码和Mac 输 ssh 密码两端都把菜单栏输入法切成 ABC（英文） 再操作。这是密码反复不对却"看起来没错"的头号原因。

排坑 5（ssh 连不上/无响应：本镜像用的是 OpenSSH 的 sshd，不是 dropbear）：本 SAMA5D27 Buildroot 镜像的 SSH 服务端是 OpenSSH（/usr/sbin/sshd），没有 dropbear。若 ssh root@IP 报 Connection refused/超时、或重启后突然连不上，通常是 sshd 没在跑。先确认到底有没有 sshd：

  • ls /etc/init.d/ | grep -i ssh — 应能看到 S50sshd 开机脚本。
  • ls -l /etc/ssh/ — 应有 sshd_config 和 ssh_host_*_key 等 host key。

概念：为什么 Mac 有这么多 en 接口？到底用哪个？

macOS 会把每一种网络能力都暴露成独立接口（都叫 en 开头）：Wi‑Fi、Thunderbolt 桥、外接 USB 网卡、VPN 隧道、AirDrop 等。所以一台 Mac 上能看到 en0~en4、en12/en14、utun0~5、awdl0 一大堆，这很正常。

en 是什么意思？它等于 MAC 地址吗？ en 是 Ethernet（以太网）的缩写，是 BSD/macOS 内核给网络接口起的软件编号（en0、en1… 按探测顺序排）。它不是 MAC 地址，但两者有关系——每个 en 接口背后通常对应一块物理网卡，那块网卡有自己的 MAC 地址（在 ifconfig 里叫 ether xx:xx:xx:xx:xx:xx）：

概念是什么ifconfig 中的样子本机例子
接口名 enX操作系统给接口的软件编号en0: / en14:en14
MAC 地址烧在网卡硬件上的全球唯一物理地址ether xx:xx:xx:xx:xx:xxether e4:66:e5:92:ff:4b（en14 的身份证）

关系一句话：en14 是"这个口叫什么名字"（软件起的），e4:66:e5:92:ff:4b 是"这块硬件是谁"（出厂烧录）。例外：并非所有 en 都对应真实硬件——bridge0、带 PROMISC 的 en1/en2（Thunderbolt 桥）、utun*（VPN 隧道）是纯软件虚拟接口，没有独立物理 MAC。只有真正插了硬件的 en（如你的 en14）才对应一块实体网卡。

你这台机器（ChengdeMacBook-Air-2）上：en0 是 Wi‑Fi 上网口（192.168.1.108，不能动）；en14 是插板子的外接以太网适配器（显示 169.254.x 链路本地地址）；其余 en1/en2/bridge0 是 Thunderbolt 内部桥接，utun*/awdl0 是 VPN/AirDrop，都和直连无关。

怎么选？——判断规律（拿到任意一台 Mac 的 ifconfig 输出都能照此判断）

  1. 先定位"插了网线的口"：网线已插、接口已 up，但暂时还没 DHCP 给它发正常 IP 时，系统会给自己分配一个 169.254.x.x 链路本地地址。凡是显示这个地址的接口，就是连着板子的以太网口（本机是 en14）。这是最准的判定依据。
  2. 排除"正在上网的口"：带 192.168.x.x / 10.x.x.x / 172.16~31.x 且能正常上网的接口（本机 en0=Wi‑Fi 192.168.1.108）绝对不要碰——给它配静态 IP 会直接断网。
  3. 排除系统虚拟接口：utun0~n（VPN 隧道）、awdl0/llw0（AirDrop/接力）、lo0（回环）、gif0（隧道）都和直连无关。
  4. 排除内部桥接：bridge0 以及带 PROMISC 标志的 en1/en2 通常是 Thunderbolt 桥接，系统内部用。
  5. 编号会变，别记死：USB 网卡换个 USB 口，编号可能是 en12、en14 甚至别的。以每次 ifconfig 实际看到的为准，或用下面的命令一键定位。

共享上网原理图解（动手前先建立直觉）

先把三个最容易混的概念用一句话分清（en / MAC 的详细对比见上方"为什么 Mac 有这么多 en 接口"概念框）：

  • en = 接口名（插座编号）：macOS 给每个"网络插座"编的号，插 Wi‑Fi 的是一个、插 USB 网卡的是另一个。板子用的是 en14 这个插座。
  • MAC 地址 = 硬件身份证（出厂烧死）：e4:66:e5:92:ff:4b 是烧在网卡里的全球唯一地址，改不了，用来在同一根网线内区分谁是谁。
  • IP 地址 = 临时门牌号（会变）：192.168.2.1 这种是网络里互相找的"门牌"。换 Wi‑Fi、重连一下就可能变——MAC 是"你是谁"，IP 是"你现在住哪"，两回事。

为什么 Mac 上这么多 en？因为 Mac 把每种上网能力都暴露成独立接口：Wi‑Fi、USB 网卡、Thunderbolt 桥、VPN、AirDrop…… 你真正要关心的只有两个：en0（连家里路由器上网）和 en14（插板子的 USB 网卡），其余都是系统内部虚拟的。下面两张图把"你的 Mac 真实接口"和"板子数据怎么经共享桥出去"画清楚。

板子的数据是怎么和共享桥联系起来的？ 关键在于：en14 是 bridge 的成员端口，bridge 把板子和 Mac 自己"接在同一个虚拟交换机上"。所以板子发出的数据帧从网线进 en14 → 被交给 bridge100 虚拟交换机 → bridge 二层转发给"桥上的 Mac"（192.168.2.1）→ Mac 内核做 NAT 把源 IP 改写成自己的 Wi‑Fi 地址 → 从 en0 发往互联网。回程完全反过来。这也解释了为什么 en14 自己不需要 IP——它只是 bridge 里专门"接板子那根网线"的二层搬运工，IP 配在桥上而非物理口上，是 macOS bridge 模式的正常设计。

网络概念提炼总结（mac / ip / en / bridge / ARP 一图看懂）

概念 一句话 你机器上的真实值
en 接口名 = 插座编号，系统给每个网口编的号 en0 = Wi‑Fi 上网；en14 = 连板子的 USB 网卡
MAC 硬件身份证，出厂烧死、全球唯一、不可变 en14 的 MAC = e4:66:e5:92:ff:4b
IP 临时门牌，可变，用来跨网络找路 板子 192.168.2.2；Mac 桥 192.168.2.1
bridge Mac 建的虚拟交换机，把 en14 和 Mac 自己接成同一局域网 bridge100，IP 192.168.2.1 配在桥上

为什么 MAC 和 IP 都得有？ 寄快递要两层地址：外层写"这一步送到谁"（MAC，邻居地址，只在同一根线有效），内层写"最终送到哪"（IP，有结构的门牌，路由器靠它跨网络找路）。缺 MAC → 同一根线上分不清包给谁，本地瘫痪；缺 IP → 没有结构化地址，出不了局域网。所以数据包是"MAC 套着 IP"一起走：MAC 每跳重写，IP 目的端到端不变。

ARP：已知 IP，怎么查到 MAC

板子只知道网关 IP 192.168.2.1，但网线上只能按 MAC 投递，于是：① 先查本机 ARP 缓存（arp -n），命中即用；② 未命中就广播请求（目的 MAC = FF:FF:FF:FF:FF:FF），问"谁是 192.168.2.1"；③ 同网段只有 IP 匹配的 Mac bridge100 单播应答自己的 MAC；④ 板子写入缓存并设过期时间。关键：ARP 不出网段，板子永远只问网关的 MAC，绝不会去问 8.8.8.8 的 MAC。

数据帧里 MAC 和 IP 各扮演什么角色（板子 ping 8.8.8.8）

真正在线上跑的是 MAC 帧，IP 包只是帧里"装的一封信"。板子发往网关时，先经 ARP 拿到网关 MAC，再把 IP 包（目的 8.8.8.8）装进目的 MAC = 网关的帧里发出；Mac 做 NAT 改写源 IP 后重新封装再发往互联网。

网关是什么？为什么"MAC 不出网关"

网关 = 连接两个不同网络的"大门 / 中转站"（通常是路由器）。板子待在小局域网 192.168.2.x，互联网在另一网络，板子过不去，必须先把包交给网关。本场景网关就是 Mac 的 bridge100，IP = 192.168.2.1。精确地说：MAC 是同一段链路内的地址，每经过一个网关就被重写——帧①目的 MAC 填的是网关 MAC（板子先把包交给网关），过了 Mac 这扇门后帧②目的 MAC 已换成路由器 MAC，板子原来的 MAC 被留在了这一侧。这正好呼应 ARP 不出网段：ARP 只能在本局域网广播，所以只问得到网关的 MAC，问不到外网 8.8.8.8 的 MAC，板子也不需要知道它。

先抛开 bridge：普通电脑经家用路由器访问 Google

bridge 只是 Mac 把"路由器 + DHCP + 交换机"合一的特例，反而容易绕。最朴素的模型是：电脑连家用路由器，路由器再连互联网。电脑看 142.250.x.x 不在自家 192.168.1.x 小网，就知道"先交给网关 192.168.1.1"。① 电脑 ARP 问出网关 MAC（R1），封装帧：目的 MAC = R1、目的 IP = Google；② 路由器拆看 IP 发现要去外网，做 NAT 改写源 IP，重新封装新帧从 WAN 口发出：目的 MAC 换成运营商下一跳、目的 IP 仍是 Google 不变。每过一台路由器 MAC 重写一次，IP 目的始终 Google。这和你板子经 Mac 上网机制完全一样：

角色 普通家用路由器 你的共享上网
内网设备电脑 192.168.1.10板子 192.168.2.2
网关路由器 LAN 192.168.1.1Mac bridge100 192.168.2.1
出网口路由器 WAN → 互联网Mac en0 Wi‑Fi → 互联网
核心机制先把包交给网关（ARP 问网关 MAC），网关 NAT 后转发；MAC 逐跳换、IP 目的不变

NAT 全称与"为什么改源 IP"

NAT = Network Address Translation（网络地址转换）。它把"内网私有地址 ↔ 外网公用地址"互相翻译。为什么路由器要把源 IP 从 192.168.1.10 改成自己的公网 IP？因为 192.168.1.x 这类私有地址（还有 10.x、172.16.x）互联网上不认、不全局唯一——Google 回包写 192.168.1.10，但无数局域网都在用同样的地址，没有路由器知道它在哪，包被丢弃，你收不到回复。改成路由器全球唯一公网 IP 后，回包能准确送回网关，再凭 NAT 映射表（内网 IP:端口 ↔ 公网 IP:端口）反查转交真正的内网设备。Google 全程只跟路由器公网 IP 对话，看不见你的私有地址。这正是上面数据帧里"Mac NAT 改写源 IP"那一步的原因。

路由器为什么有两个 MAC（双网卡）

家用路由器本质是"有两个网络接口的小电脑"：LAN 口（接你家设备，独立网卡 + MAC R1）、WAN 口（接运营商，另一块独立网卡 + MAC R2）。两套网卡硬件，各一个 MAC——就像你的 Mac 有 en0 和 en14 各一个 MAC。常见误解"一个路由器共用一个 MAC"是错的。电脑发帧目的 MAC = LAN 口 R1；帧经路由器 CPU 后重封装，目的 MAC 换成 WAN 侧下一跳、源 MAC 换成 R2；LAN MAC / WAN MAC 在互联网侧从不出现，各管各的一段链路。

最具体版：逐跳信封链（MAC 每段重写，IP 始终指 Google）

把上面所有概念落到"每个帧的 4 个字段"上。假设电脑 192.168.1.10（MAC 电脑A）、路由器 LAN 192.168.1.1（MAC 路由L）/ WAN 公网 203.0.113.5（MAC 路由W）、运营商下一跳 MAC 运营X、Google 142.250.1.1（MAC 谷歌G）：

一句话串起来： en 是插座、MAC 是身份证、IP 是门牌、bridge 是虚拟交换机、网关是连接内外网的大门；ARP 用 IP 查 MAC（且只在本网段）；数据包出门时 MAC 套着 IP——MAC 每跳重写（过网关必换、出不了网关这一侧），IP 目的端到端不变；NAT 把私有源 IP 翻成路由器公网 IP 以便外网回包。你当前已验证：板子 udhcpc 拿 192.168.2.2，ping 8.8.8.8 0% 丢包，共享上网打通。

12.1　启动链总览：七步接力赛

SAMA5D27 从 SD 卡启动，整个过程像一场七棒接力赛——每一棒做完自己的事，把控制权交给下一棒：

① Boot ROM（芯片内置，不可修改）
   │  读 MBR → 找到 FAT 分区 → 找到 boot.bin
   │  加载 boot.bin 到 SRAM 0x300000
   ▼
② boot.bin / AT91Bootstrap（14KB，跑在 SRAM）
   │  初始化 DDR 内存
   │  从 FAT 分区读 u-boot.bin → 写入 DDR 0x23f00000
   │  跳转到 0x23f00000
   ▼
③ U-Boot（484KB，跑在 DDR）
   │  执行 bootcmd 环境变量
   │  fatload 读 dtb → DDR 0x21000000
   │  fatload 读 zImage → DDR 0x22000000
   │  bootz 跳转到内核
   ▼
④ Linux 内核（4.7MB，跑在 DDR）
   │  解析 dtb（设备树），初始化硬件驱动
   │  读 bootargs：root=/dev/mmcblk0p2
   ▼
⑤ 挂载根文件系统（rootfs.ext2 分区）
   │  执行 /sbin/init
   ▼
⑥ 用户空间启动
   │  登录提示符出现在串口
   ▼
⑦ 你可以输入命令了

关键特征：每一级的地址都是上一级在编译时写死的——Boot ROM 的 SRAM 地址是芯片硬件固定的，boot.bin 的 DDR 地址是 AT91Bootstrap 编译时配置的，U-Boot 的 dtb/zImage 地址是 bootcmd 环境变量里写死的，内核的 root 设备是 bootargs 命令行参数指定的。全链路没有任何动态协商。

12.2　MBR：SD 卡的"目录页"

MBR（Master Boot Record，主引导记录）是 SD 卡的第一个扇区，也就是整张卡最开头的 512 个字节。它是整个启动链的起点——Boot ROM 上电后做的第一件事就是读这 512 个字节。

用一本书来比喻：SD 卡就像一本厚书，MBR 就是这本书的目录页。目录页告诉你这本书分了几个章节（分区）、每个章节从第几页开始（分区起始位置）、每个章节有多长（分区大小）。

MBR 的 512 字节结构

偏移长度名称内容
0x000446 字节启动代码（Boot Code）PC 上放 BIOS 引导程序；SAMA5D27 上全为 0，因为 Boot ROM 不从这里执行代码
0x1BE64 字节分区表（Partition Table）4 个分区表项，每个 16 字节，描述 4 个分区
0x1FE2 字节魔数（Magic Number）固定为 55 AA，Boot ROM 用它判断"这是一张有效的启动卡"

为什么启动代码 446 字节全是 0？

在 PC 上，BIOS 会读 MBR 的前 446 字节到内存并执行（那里放了一段引导程序）。但 SAMA5D27 的 Boot ROM 不执行 MBR 里的代码——它有自己的逻辑：读 MBR 只是为了看分区表。所以这 446 字节对 SAMA5D27 来说没用，Buildroot 填 0 即可。

为什么偏偏是 446 字节？

这是历史遗产：512（扇区大小）- 64（分区表）- 2（魔数）= 446。1980 年代 IBM PC 设计 MBR 时就这么定的，后来成了标准，所有遵循 MBR 标准的设备都沿用这个布局，SAMA5D27 也不例外。

为什么分区表是 2 个分区而不是 4 个？

MBR 分区表最多能描述 4 个分区（64 字节 ÷ 16 字节/项 = 4 项），但不要求必须填满。SAMA5D27 的 sdcard.img 只需要 2 个分区（boot.vfat + rootfs.ext2），所以只用了 2 项，剩下 2 项全填 0。Boot ROM 扫到分区类型为 0x00（空）就跳过。

📖 十六进制偏移详解：0x1BE 和 0x1FE 是怎么算出来的？（点击展开）

十六进制地址的计算：

偏移 0x000 = 十进制 0     → 启动代码起始
偏移 0x1BE = 十进制 446   → 分区表起始
  0x1BE = 1×256 + 11×16 + 14 = 256 + 176 + 14 = 446
偏移 0x1FE = 十进制 510   → 魔数起始
  0x1FE = 1×256 + 15×16 + 14 = 256 + 240 + 14 = 510
偏移 0x200 = 十进制 512   → MBR 结束（下一个扇区开始）

所以：446 + 64 + 2 = 512，刚好一个扇区。

12.3　分区表 16 字节解析：如何找到 FAT 分区的物理地址

分区表有 4 项，每项 16 字节。我们只看第一项（分区 1: boot.vfat）的 16 字节，这是 Boot ROM 最关心的：

字节长度名称值含义
B01启动标志0x800x80 = 可启动分区，0x00 = 不可启动
B1-B33CHS 起始—磁头/柱面/扇区（老式寻址，SAMA5D27 不用）
B41分区类型0x0C0x0C = FAT32 LBA / 0x06 = FAT16 / 0x83 = Linux ext4
B5-B73CHS 结束—同上，不用
B8-B114LBA 起始扇区00 08 00 00小端序，实际值 0x00000800 = 2048
B12-B154扇区总数00 00 00 01小端序，实际值 0x01000000 = 16,777,216... 不对，见下

什么是小端序（Little-Endian）？

计算机存储多字节数值时有两种顺序：

  • 大端序（Big-Endian）：高位在前，像人类读数字。0x00000800 存为 00 00 08 00
  • 小端序（Little-Endian）：低位在前，像反着读。0x00000800 存为 00 08 00 00

ARM 和 x86 都用小端序。所以分区表里 00 08 00 00 要反过来读：0x00000800 = 2048。

📖 小端序怎么读？详细拆解（点击展开）

4 个字节 00 08 00 00，小端序的读法是从右往左拼：

内存中的字节：B8=00  B9=08  B10=00  B11=00

小端序读取（低位在前）：
  最低位字节 = B8  = 0x00
  次低位字节 = B9  = 0x08
  次高位字节 = B10 = 0x00
  最高位字节 = B11 = 0x00

拼成 32 位值：0x00_00_08_00 = 0x00000800

十进制 = 8×256 = 2048

也就是说：这个分区从第 2048 个扇区开始。

从 LBA 到物理地址：分区到底在 SD 卡的哪个位置？

LBA（Logical Block Addressing）是扇区编号，每个扇区 512 字节。Boot ROM 算物理地址的方式：

分区 1 起始 LBA = 2048
每个扇区 = 512 字节

物理字节偏移 = LBA × 512 = 2048 × 512 = 1,048,576 字节 = 1MB

所以 boot.vfat 分区从 SD 卡的第 1MB 位置开始

为什么从 1MB 开始？前 1MB 是"留白区"：512 字节给 MBR，剩下 ~1MB 空着。这是 PC 分区的惯例（4K 对齐 + 给引导程序留空间），Buildroot 沿用了这个约定。

Boot ROM 的完整查找流程：

  1. 读 SD 卡第 0 扇区（MBR），检查最后 2 字节是否 55 AA
  2. 扫描 4 个分区表项，找启动标志 = 0x80 且 分区类型 = FAT（0x06/0x0C/0x0E）的分区
  3. 从分区表项的 B8-B11 读出 LBA 起始扇区（小端序）= 2048
  4. 跳到 SD 卡的 2048 × 512 = 1MB 位置，这里就是 FAT 分区的开头
  5. 用内置的极简 FAT 文件系统读取器，在 FAT 分区里按文件名查找 boot.bin
  6. 找到后，把 boot.bin 的内容加载到 SRAM 地址 0x300000
  7. 跳转到 0x300000，开始执行 boot.bin
📖 分区类型 0x0C 和 0x06 有什么区别？（点击展开）

都是 FAT 类型，区别在于是否使用 LBA 寻址：

  • 0x06 = FAT16（传统 CHS 寻址）
  • 0x0E = FAT16 LBA
  • 0x0C = FAT32 LBA
  • 0x83 = Linux（ext2/ext3/ext4）

Boot ROM 只关心"是不是 FAT 类型"，不区分 0x06/0x0C/0x0E。第二个分区（rootfs.ext2）的类型是 0x83（Linux），Boot ROM 会跳过它——因为 Boot ROM 只找 FAT 分区里的 boot.bin。

├── sbin/      ← 系统命令（init, reboot...）
├── usr/       ← 用户程序和库
├── lib/       ← 动态链接库（.so 文件）
├── etc/       ← 配置文件
├── dev/       ← 设备节点
├── root/      ← root 用户家目录
└── var/       ← 日志、缓存

文件和分区的关联逻辑：

  • 分区 1 是 FAT 格式，因为 Boot ROM、AT91Bootstrap、U-Boot 都内置了 FAT 读取器，能按文件名读文件
  • 分区 2 是 ext4 格式，因为 只有 Linux 内核有 ext4 驱动，U-Boot 不认 ext4
  • 所以引导阶段的文件（boot.bin、u-boot.bin、zImage、dtb）必须放 FAT 分区，内核启动后才切到 ext4 分区

12.5　boot.bin（AT91Bootstrap）：谁启动的？地址谁决定的？

Boot ROM 把控制权交给 boot.bin 后，boot.bin 自己就开始自主运行了——它的 main() 函数按源代码写死的流程执行，不需要谁"启动"它或"告诉"它做什么。

boot.bin 干三件事：

  1. 初始化 DDR 控制器 — 配置时钟、时序、bank 映射，让 128MB DDR2 可用
  2. 从 FAT 分区读 u-boot.bin — 用内置 FAT 读取器，按文件名找到 u-boot.bin（484KB），读到 DDR
  3. 跳转到 u-boot.bin 执行 — 设置 PC 指针，CPU 开始跑 U-Boot

三个关键宏定义（编译时写死）

DDR 地址 0x23f00000 不是运行时协商出来的，而是在 Buildroot 编译 AT91Bootstrap 时，通过板级头文件 sama5d27_som1_ek.h 里的宏定义烤进二进制的：

宏定义值含义类比
CONFIG_BOOTSTRAP_MAXSIZE 0xC000 (48KB) boot.bin 自身的最大体积限制。因为 SRAM 只有 128KB，boot.bin 不能太大。实际只用了 14KB 行李箱限重 48 公斤
CONFIG_LOAD_ADDR 0x23f00000 u-boot.bin 写入 DDR 的目标地址。boot.bin 从 SD 卡读出 u-boot.bin 后，memcpy 到这个地址 快递收货地址
CONFIG_JUMP_ADDR 0x23f00000 加载完后跳转到此地址执行。PC = 这个地址，CPU 开始跑 U-Boot 走到哪个房间办公

为什么 LOAD_ADDR 和 JUMP_ADDR 相同？

因为 U-Boot 直接加载到它将要执行的位置，不需要搬运第二次。如果两者不同，boot.bin 还要多做一次 memcpy，没必要。

用 C 代码理解 boot.bin 的逻辑（简化版）：

// boot.bin 的 main() 函数（简化）
int main() {
    // 第 1 步：初始化 DDR 控制器
    ddr_init();

    // 第 2 步：从 SD 卡 FAT 分区读 u-boot.bin
    //   CONFIG_LOAD_ADDR = 0x23f00000 是写入目标地址
    fat_read_file("u-boot.bin", (void *)0x23f00000);

    // 第 3 步：跳转到 DDR 执行
    //   CONFIG_JUMP_ADDR = 0x23f00000 是跳转目标
    void (*entry)(void) = (void (*)(void))0x23f00000;
    entry();  // PC = 0x23f00000, 开始执行 U-Boot

    return 0;  // 永远不会到这里
}
📖 0xC000 怎么换算成 48KB？（点击展开）

十六进制 0xC000 转十进制：

0xC000 = C × 16³ = 12 × 4096 = 49,152 字节

49,152 ÷ 1024 = 48 KB

快速换算表：

大小字节十六进制
1 KB1,0240x400
4 KB4,0960x1000
16 KB16,3840x4000
48 KB49,1520xC000
128 KB131,0720x20000
1 MB1,048,5760x100000

规律：每乘以 16，十六进制左移一位加 0。记住 1KB = 0x400，其他都能推。

📖 0x300000 + 128KB = 0x320000 怎么算的？（点击展开）

SRAM 起始地址 0x300000，大小 128KB，结束地址 = 起始 + 大小：

128 KB = 131,072 字节

131,072 转十六进制 = 0x20000

  0x300000    （SRAM 起始）
+ 0x020000    （128KB = 0x20000）
----------
  0x320000    （SRAM 结束）

十六进制加法逢 16 进 1：00000 + 20000 = 20000，3 + 0 = 3，结果 0x320000。

SRAM 地址范围：0x300000 ~ 0x31FFFF（注意结束地址是排他的，0x320000 是"下一个地址"）。

📖 为什么 DDR 地址是 0x23f00000？（点击展开）

SAMA5D27 的 DDR2 内存映射从 0x20000000 开始，总共 128MB，到 0x28000000 结束。

DDR 内存的地址分配：

0x20000000 ┬── DDR 起始
           │
0x21000000 ├── dtb（设备树）       ← U-Boot bootcmd 写入
0x22000000 ├── zImage（内核）      ← U-Boot bootcmd 写入
           │   ...
0x23f00000 ├── u-boot.bin          ← AT91Bootstrap 写入
           │
0x28000000 ┴── DDR 结束（128MB）

0x23f00000 - 0x20000000 = 0x03F00000 = 63 MB
→ U-Boot 放在 DDR 的第 63MB 位置（高地址区）

U-Boot 放在高地址，避免和后面的 dtb（0x21000000）和内核（0x22000000）冲突。

12.6　U-Boot：加载内核和设备树

U-Boot 跑在 DDR 里，空间充足（128MB），功能比 boot.bin 强大得多。它执行预设的 bootcmd 环境变量，完成最后的引导工作。

bootcmd 命令详解

bootcmd=fatload mmc 0 0x21000000 at91-sama5d27_som1_ek.dtb; \
       fatload mmc 0 0x22000000 zImage; \
       bootz 0x22000000 - 0x21000000

分三条命令，用分号 ; 连接，顺序执行：

命令含义效果
fatload mmc 0 0x21000000 ...dtb 从 SD 卡（mmc 0）的 FAT 分区，读 at91-sama5d27_som1_ek.dtb 文件，写入 DDR 地址 0x21000000 设备树加载到 DDR
fatload mmc 0 0x22000000 zImage 从 SD 卡的 FAT 分区，读 zImage 文件，写入 DDR 地址 0x22000000 内核镜像加载到 DDR
bootz 0x22000000 - 0x21000000 跳转到 0x22000000 执行内核。- 表示没有 ramdisk，第三个参数 0x21000000 是 dtb 地址 内核开始运行
📖 bootcmd 里的地址是谁定的？（点击展开）

这些地址是 U-Boot 编译时通过环境变量配置写死的。在 Buildroot 编译 U-Boot 时，板级配置文件（如 include/configs/at91-sama5d27_som1_ek.h）里定义了默认环境变量：

#define CONFIG_BOOTCOMMAND "fatload mmc 0 0x21000000 ..."
#define CONFIG_EXTRA_ENV_SETTINGS \
    "loadaddr=0x22000000\0" \
    "dtbaddr=0x21000000\0" \
    "bootargs=console=ttyS0,115200 root=/dev/mmcblk0p2 rw"

这些值在 make 编译时被嵌入 U-Boot 二进制。板子上电后，U-Boot 读取自己内部的默认环境变量来执行。

你也可以在 U-Boot 命令行里用 setenv 临时修改（掉电丢失），或 saveenv 保存到 SD 卡的 U-Boot 环境变量区域（掉电不丢）。

12.7　bootargs：内核怎么知道根文件系统在哪？

U-Boot 跳转到内核时，不仅传递了 dtb 地址，还传递了一个命令行参数字符串 bootargs：

bootargs=console=ttyS0,115200 earlyprintk root=/dev/mmcblk0p2 rw rootwait

逐个参数解释：

参数值含义
consolettyS0,115200内核日志输出到串口 0，波特率 115200。这就是你在串口终端看到内核启动日志的原因
earlyprintk—在串口驱动完全初始化之前就允许打印，方便调试早期启动问题
root/dev/mmcblk0p2根文件系统在哪个设备。mmcblk0 = SD 卡，p2 = 第 2 个分区 = rootfs.ext2
rw—以读写模式挂载根文件系统（默认是只读）
rootwait—等 SD 卡设备就绪后再挂载（SD 卡初始化可能慢，防止找不到设备）

地址传递链完整路径：

Boot ROM
  └→ SRAM 0x300000（硬件固定，芯片设计时决定）
     │
     boot.bin (AT91Bootstrap)
     └→ DDR 0x23f00000（编译时 CONFIG_JUMP_ADDR 写死）
        │
        U-Boot bootcmd
        ├→ DDR 0x21000000 = dtb（编译时环境变量写死）
        ├→ DDR 0x22000000 = zImage（编译时环境变量写死）
        └→ bootargs: root=/dev/mmcblk0p2（编译时环境变量写死）
           │
           Linux 内核
           └→ 挂载 /dev/mmcblk0p2 = 分区 2 = rootfs.ext2
              └→ 执行 /sbin/init → 用户空间启动

每一级的地址来源：

  • SRAM 0x300000 → Boot ROM 硬编码（芯片设计时固化在硅片里，不可修改）
  • DDR 0x23f00000 → AT91Bootstrap 编译时 CONFIG_JUMP_ADDR 宏定义
  • DDR 0x21000000 / 0x22000000 → U-Boot 编译时默认环境变量
  • /dev/mmcblk0p2 → U-Boot 编译时 bootargs 环境变量

全链路没有任何动态发现或协商——每个地址都是上一级在编译时写死的常量。这意味着：如果你换了不同的板子或不同的内存配置，必须重新编译对应的引导程序，修改这些地址。

12.9　内核收到 bootargs 之后：从启动参数到登录提示符

前面几节讲的是 U-Boot 怎么把 bootargs 传给内核。那么内核收到这行参数之后，做了什么？我们可以在板子上用 cat /proc/cmdline 看到内核实际收到的启动指令：

# cat /proc/cmdline
console=ttyS0,115200 earlyprintk root=/dev/mmcblk0p2 rw rootwait

逐个解读每个参数：

参数含义通俗解释
console=ttyS0,115200内核控制台 = 串口0，波特率 115200内核的"打印信息"输出到串口0，就是你用的 screen 那根线
earlyprintk启用早期打印内核启动最早期（串口驱动还没就绪时）就先把日志打出来，方便调试
root=/dev/mmcblk0p2根文件系统 = SD 卡第 2 分区内核从这里挂载 /（根目录），也就是 df -h 看到的那个分区
rw读写模式挂载允许读写（如果写 ro 则只读）
rootwait等待根设备就绪SD 卡驱动初始化需要时间，内核先等它准备好再挂载，避免启动失败

这正是 U-Boot bootargs 的最终落地：

U-Boot 设置 bootargs → 通过 ATAGS/dtb 传给内核 → 内核解析 → 写入 /proc/cmdline

所以 /proc/cmdline 就是内核实际收到的"任务清单"——U-Boot 给内核的一张指令："你的根文件系统在 SD 卡第二分区，用读写模式挂，日志打到串口，等等设备再挂载。"

收到 cmdline 后，内核做了 6 件事

内核收到 bootargs 后，还要做一大堆事情才能给你那个 # 提示符。整个过程分为内核空间（内核代码在跑）和用户空间（用户程序在跑）两个阶段：

逐步详解

① 解析 cmdline：内核收到 console=ttyS0,115200 root=/dev/mmcblk0p2 rw rootwait 这个字符串，拆解成键值对存到内部变量里。就像拆快递——把"任务清单"上的每条指令都读出来，记住"根文件系统在 mmcblk0p2"。

② 初始化内核子系统：内核先把自己"内部器官"搭好：

  • 内存管理：把 128MB DDR2 划分成可分配的页
  • 进程调度器：准备管理进程的 CPU 时间
  • 中断系统：让硬件能"打断"内核来报告事件
  • 时钟：系统节拍（tick）开始跳动

③ 初始化设备驱动：这就是第 13 节讲的设备树大显身手的地方。内核读取 dtb，发现板子上有 GPIO、MMC（SD 卡控制器）、USB、网卡等硬件，就加载对应的驱动程序。这也是 /sys/class/leds/、/dev/mmcblk0 等节点被创建的阶段——驱动注册后，设备节点就"长"出来了。

④ 挂载根文件系统：内核根据 root=/dev/mmcblk0p2，找到 SD 卡第二分区，以 rw（读写）模式挂载到 /（根目录）。从此内核就能读到文件系统里的 /sbin/init、/etc/ 等文件了。

⑤ 启动 init 进程 —— 关键转折点：内核执行 /sbin/init，这是 PID=1 的第一个用户空间进程。这一步是分水岭：

  • 之前：内核在"裸奔"，自己跑自己的代码
  • 之后：开始执行用户编写的程序

可以理解为：内核像建筑队盖好了毛坯房，init 就是第一个搬进来住的"物业经理"。

⑥ 运行启动脚本 → 登录：init 读取 /etc/inittab 配置文件，依次执行启动脚本（通常是 /etc/init.d/rcS），做这些事：

  • 配置网卡 IP
  • 挂载额外的文件系统（/proc、/sys 等）
  • 启动服务（如 SSH、Web 服务器）
  • 最终启动一个 shell，给你 # 提示符

你可以在板子上验证最后一步：

# 看 init 配置
cat /etc/inittab

# 看启动脚本跑了什么
cat /etc/init.d/rcS

这就是从内核收到 bootargs 到你看到 # 提示符的完整旅程。和我们之前讲的启动链连起来，完整链条是：

Boot ROM → boot.bin → U-Boot → 内核(解析cmdline→初始化→挂载rootfs→启动init) → 你

本节总结：SD 卡启动链是一个七级接力过程，每一级都在编译时把下一级的地址写死。MBR 只负责"指路"（告诉 Boot ROM FAT 分区在哪），之后是 Boot ROM → boot.bin → U-Boot → 内核 → rootfs 的逐级加载。内核收到 bootargs 后还有六步（解析参数→初始化子系统→初始化驱动→挂载根文件系统→启动 init→运行启动脚本），最终才出现登录提示符。理解了这个链条，你就理解了嵌入式 Linux 启动的核心原理。

13设备树、VFS 与 sysfs：从命令到硬件的完整链路

你在板子上跑了 echo 255 > /sys/class/leds/red/brightness，红灯就亮了。这一行命令从你的手指到 LED 灯珠，中间经过了多少层？这一节把整条链路彻底拆开。

13.1 设备树是什么？——U-Boot 给内核的"硬件清单"

内核启动时是"瞎子"——它不知道板子上有什么硬件、每个硬件在哪个地址。U-Boot 负责把一份"硬件清单"递给内核，这份清单就是设备树（Device Tree，dtb）。

一句话理解

设备树 = U-Boot 给内核的硬件清单。清单上写了有什么硬件、在什么地址。内核照着清单逐条创建对应的设备文件（/dev/ 和 /sys/），之后你就能用命令操作这些硬件了。

13.2 内核读 MBR 创建设备节点的过程

你在板子上跑 ls /dev/mmcblk* 看到 mmcblk0、mmcblk0p1、mmcblk0p2，这些设备节点是怎么来的？

验证这个过程：在板子上跑 dmesg | grep mmcblk0，你会看到类似 mmcblk0: p1 p2，就是内核发现并创建的 2 个分区。

13.2a 另一种创建设备节点的路径：设备树 → LED 驱动

13.2 讲的是块设备（SD 卡）靠读磁盘第 0 扇区的 MBR 分区表来创建 /dev/mmcblk* 节点。LED 这类"板级外设"走的是另一条路：硬件信息不是藏在磁盘里，而是写在设备树 DTS 里；内核加载对应的 gpio-leds 驱动，由驱动在 sysfs 下建 /sys/class/leds/<名>/。下面把"LED 驱动到底怎么创建出来"拆成四段。

图：LED 驱动创建全过程（设备树 → probe → /sys/class/leds）

注意区分：gpio-leds 驱动是跑在内核里的模块，不是你之前写的 led_blink.c（用户态程序）。它的"创建"分两大段——驱动先注册自己，再等硬件信息（设备树）对上号，才逐个建 LED 设备。

阶段一：驱动先"报名"（注册）

内核编译时（Buildroot 里选了 LEDS_GPIO），gpio-leds 驱动就被编进内核（或编成模块 leds-gpio.ko）。它本质是一个 platform driver，最关键的是这张"匹配表"：

内核驱动 · gpio-leds 注册（简化）
static const struct of_device_id of_gpio_leds_match[] = {
    { .compatible = "gpio-leds", },
    { },
};

static struct platform_driver gpio_led_driver = {
    .probe  = gpio_led_probe,        /* 对上号后调这个函数 */
    .driver = {
        .name  = "leds-gpio",
        .of_match_table = of_gpio_leds_match,
    },
};
module_platform_driver(gpio_led_driver);   /* 注册进内核 */

module_platform_driver(...) 一执行，驱动就"报名"说自己能处理 compatible = "gpio-leds" 的设备。此时它还没干任何实事，只是在内核的驱动列表里挂了号。

阶段二、三：设备树节点 → platform_device → 总线匹配

内核启动解析 DTB，发现 DTS 里有 leds { compatible = "gpio-leds"; ... }，就为这个节点生成一个 platform_device（内核里代表"一个硬件设备"的结构体），把 compatible 和子节点信息塞进去。随后 platform 总线把刚生成的 device 和已注册的 driver 做匹配：比对 compatible 字符串，一致 → 内核自动调用驱动的 probe()。

阶段四：probe 里为每个 LED 建"类设备"（核心）

gpio_led_probe() 做的事，简化成你能懂的伪代码：

内核驱动 · gpio_led_probe()（简化伪代码）
static int gpio_led_probe(struct platform_device *pdev)
{
    for_each_child_of_node(pdev->dev.of_node, child) {
        struct gpio_led_data *led = devm_kzalloc(...);

        /* ① 读 gpios 属性，向 GPIO 子系统申请该脚、设为输出 */
        led->gpiod = devm_get_gpiod_from_child(dev, NULL, child);
        gpiod_direction_output(led->gpiod, 0);

        /* ② 读 label（没有就用节点名 "red"）作为 LED 名字 */
        led->cdev.name = of_get_property(child, "label", NULL) ?: child->name;

        /* ③ 把"怎么改亮度"的函数指针挂上去 */
        led->cdev.brightness_set = gpio_led_set;

        /* ④ 注册进 LED 子系统 → 在 /sys/class/leds/ 下建目录+属性文件 */
        led_classdev_register(&pdev->dev, &led->cdev);
    }
    return 0;
}

第 ④ 步的 led_classdev_register() 才真正让"LED 设备"存在——它在 /sys/class/leds/ 下创建 red/ 目录，并生成 brightness、max_brightness、trigger 几个属性文件。而第 ③ 步挂上去的 gpio_led_set() 回调，里面只有一句真正干活的话：

内核驱动 · 真正翻转电平的回调
static void gpio_led_set(struct led_classdev *cdev, enum led_brightness value)
{
    struct gpio_led_data *led = cdev_to_gpio_led_data(cdev);
    gpiod_set_value(led->gpiod, value ? 1 : 0);  /* ← 翻转 GPIO 物理电平 */
}

串起来：你 echo 255 时发生了什么

这正好接上 13.4 的六层链路，现在你看清了"驱动层"具体是谁在动：

你 echo 255 时，内核里发生的事
echo 255 > /sys/class/leds/red/brightness
   │  (sysfs 属性写)
   ▼
led_brightness_store()              ← LED 子系统
   ▼
cdev->brightness_set(cdev, 255)     ← 调用 probe 里挂的 gpio_led_set
   ▼
gpiod_set_value(gpiod, 1)           ← GPIO 子系统
   ▼
PIOA 控制器写寄存器                  ← 硬件：灯亮

你写的 led_blink.c 只是在最顶上"写文件"，真正的"翻电平"是 gpio_led_set 这一行。

维度 13.2 mmcblk0p1 LED 设备

        gpios = <&pioA 28 1>;        /* 蓝灯接在 GPIO A 第 28 脚 */
        default-state = "off";
    };

        label = "green";
        gpios = <&pioA 29 1>;        /* 绿灯接在 GPIO A 第 29 脚 */
        default-state = "on";         /* 开机时灯亮 */
    };
};

绿灯为什么关不掉？

绿灯的 brightness 写 0 后值确实变了，但灯还亮——说明绿灯在硬件上直连电源，没有接到 GPIO 引脚上（或者设备树里写了但实际电路不走 GPIO）。软件层面能创建文件、改值，但物理电路上灯永远通电。

13.5 VFS 和 sysfs 是什么

VFS（虚拟文件系统）= 公司前台

Linux 里有个规矩：访问所有东西都用文件的方式。看硬盘打开 /dev/sda，看内存读 /proc/meminfo，控制灯写 /sys/class/leds/red/brightness。但这些东西本质完全不同。VFS 就是中间的翻译层——不管你访问什么"文件"，它都提供统一的 open → read/write → close 接口，然后在背后帮你转交给对应的处理模块。

sysfs = 设备管理部门

sysfs 是 VFS 下的一个具体部门，专门管硬件设备。它把内核里所有的设备、驱动都变成文件，放在 /sys/ 目录下。你在板子上看到的 /sys/class/leds/red/brightness 就是 sysfs 创建的。

13.6 sysfs 注册机制：谁注册谁响应

sysfs 的工作方式是：谁注册了文件，写操作就转交给谁。驱动程序启动时主动告诉 sysfs："我要创建一个文件，以后有人写这个文件，请通知我。"这个过程叫注册。

内核 LED 驱动代码（简化）
// 1. 定义"写文件时该干什么"
void red_brightness_write(const char *buf) {
    int value = atoi(buf);           // 把 "255" 变成数字 255
    if (value > 0)
        gpio_set_value(27, 1);       // 点亮
    else
        gpio_set_value(27, 0);       // 熄灭
}

// 2. 把函数和文件名打包在一起
struct attribute red_attr = {
    .name  = "brightness",              // 文件名叫 brightness
    .write = red_brightness_write,      // 写时调用这个函数
};

// 3. 注册到 sysfs
sysfs_create_file("/sys/class/leds/red/", &red_attr);
// → sysfs 在注册表里加一行

14常见问题 FAQ（实战踩坑记录）

make 报错：CROSS_COMPILE environment variable must be defined

没设交叉编译器环境变量。解决：

export CROSS_COMPILE=arm-linux-gnueabihf-
export ARCH=arm

建议写进 ~/.bashrc（容器内的）一劳永逸。

编译 U-Boot 报错：gnutls/gnutls.h: No such file or directory

缺少加密库开发头文件。解决：

apt update && apt install -y libgnutls28-dev
make -j$(nproc)

装完直接重编，无需 make clean。

git clone 提示 Username for 'https://github.com'

大概率是 URL 打错了（比如结尾 .gi 少了 t），git 把它当成需要认证的私有仓库。按 Ctrl+C 退出，仔细核对完整 URL（.git 结尾）。

at91bootstrap 编译成功但找不到 binaries/ 目录

4.0.x 新版产物路径改为 build/binaries/。用 find . -name "*.bin" -ls 定位。

找不到 sama5d27_som1_ek.dtb 设备树文件

linux-6.1-mchp 分支的设备树还是老命名：文件叫 at91-sama5d27_som1_ek.dtb，直接在 arch/arm/boot/dts/ 目录下（没有 microchip/ 子目录）。不确定时用：

find arch/arm/boot/dts -name "*sama5d27*"
Buildroot 报 "Can't find sama5d27_som1_ek_mmc_defconfig"

buildroot-at91 仓库的配置名带厂商前缀和版本后缀，SAMA5D27 SOM1 EK 实际叫 atmel_sama5d27_som1_ek_mmc_dev_defconfig。不确定时先列出可选配置：

ls configs/ | grep sama5d2
Buildroot 编译报 "Permission denied"（Error 126，如 compile_et）

原因：/work 是 macOS 目录的挂载点，Docker Desktop 的文件系统（gRPC-FUSE / virtiofs）在生成脚本时可能丢失可执行权限位。Buildroot 编译过程中会生成脚本再立刻执行（如 e2fsprogs 的 compile_et），权限位丢失就报 Error 126（文件存在但不可执行）。

快速修复（对单个文件）：

chmod +x output/build/host-e2fsprogs-1.46.5/lib/et/compile_et
make -j$(nproc)

根治方案——用 O= 参数把构建输出搬到容器内部目录，源码和下载缓存（dl/）留在 /work 不受影响：

mkdir -p /root/br-out
make O=/root/br-out atmel_sama5d27_som1_ek_mmc_dev_defconfig
nohup make O=/root/br-out -j$(nproc) > /root/build.log 2>&1 &
tail -f /root/build.log

编完记得把产物拷回挂载目录，Mac 上才能烧录：

cp /root/br-out/images/sdcard.img /work/
编译成功的标志是什么？

命令结束后回到提示符，且最后没有 Error。AT91Bootstrap 额外会打印 [Succeeded] It's OK to fit into SRAM area。最终以"产物文件存在且有合理大小"为准（见第 10 节验证命令）。

编译到一半能切出去做别的事吗？

能。新开终端标签（Cmd+T）即可，编译继续。但不要关闭原终端窗口、不要按 Ctrl+C（会杀掉编译进程）。

spl/u-boot-spl.bin 不存在，是失败了吗？

不是。SAMA5D27 的启动链用 AT91Bootstrap 承担第一级引导，此配置下 U-Boot 不需要 SPL。u-boot.bin（约 470KB）存在即成功。

容器重启后编译环境还在吗？

在。容器是持久化的：装过的软件包、源码、编译产物都保留。只有 export 的环境变量会丢（所以建议写进 bashrc）。用 ~/sama5/enter.sh（Mac 端）随时回到环境。
